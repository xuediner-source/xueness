## What was built

A per-tool wall-clock deadline that charges **active tool execution time only**. Time a nested model request spends queued does not count toward the budget, matching the upstream `ToolDeadline` contract (`model_request_queued` pauses, `model_request_admitted` resumes, timeout reports carry `queuedMs`).

### New module: `ts/packages/tool-bridge/src/tool-deadline.ts` (186 lines)

- `ToolDeadline` — budget bookkeeping with `pause()` / `resume()` mapped to the queued/admitted vocabulary:
  - While paused the countdown never fires (no false timeout from queue time); the paused span accumulates into `queuedMs` (live-updating getter).
  - `resume()` restarts the timer on the remaining budget; if the budget is already exhausted it expires immediately.
  - External `AbortSignal` wins **immediately, even while paused**; `expired` and `cancelled` are mutually exclusive (first wins).
  - `race(run)` lets the run's own settlement win when it comes first, then freezes further transitions; a hanging run is ended at expiry with `ToolDeadlineExceededError` (code `tool_timeout`) or, on external cancel, `ToolDeadlineCancelledError` (code `cancelled`).
  - `signal` — a stable combined signal (expiry reason carries the structured error) tools observe.
- `deadlineFailure(tool, error)` — timeout failure with `error.code = "tool_timeout"`, `data = { timedOutAfterMs, queuedMs, activeMs }`, and `queuedMs` stated in the message: queue duration is separated from execution duration in the settlement.

## Acceptance vs. brief

- "Charge only actual tool execution time" — active-only budget, verified by test.
- "Nested queueing must not false-timeout" — 120 ms queued inside a 60 ms budget leaves the run alive; expiry lands only after the remaining ~35 ms of active time, with `queuedMs >= 100` reported.
- "Cancel/AbortSignal always takes effect immediately" — tested both while paused (rejects far before remaining budget) and while active.
