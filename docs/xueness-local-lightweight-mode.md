# 本地模型轻量模式

在供应商配置或 CLI 使用 `--lightweight` 启用。轻量模式提供精简工具、按需发现、分页结果和有界上下文，适合本地模型工作流。

输入预算由模型上下文容量减去输出与安全预留得到。接口报告有效 usage 后，宿主校准估算；轻量模式的流式请求默认发送 `stream_options.include_usage` 以取得 usage。接口以 400 或 422 拒绝时，宿主去掉该字段重试一次，成功后把这一结果记在该模型配置里，重启后也不再发送（重新保存配置会清除这条记录）；模型设置中的开关可以明确打开或关闭，明确的选择不会被自动调整。缓存 Token 是输入子集，不重复计入输入总量。缺少 usage 时保留估算，不伪造实际消耗。

对本机地址（127.0.0.1 或 ::1）的模型配置，对话测试成功后会探测本地推理服务：Ollama（`/api/show`、`/api/ps`）、llama.cpp（`/props`、`/v1/models`）和 LM Studio（`/api/v1/models`，旧版为 `/api/v0/models`）。探测读取模型实际加载的上下文窗口、模型上限和是否支持原生工具调用，并与配置比较。配置的窗口大于服务实际窗口时，超出的部分会被服务端截断，界面会提示并给出建议值；模型不支持原生工具调用时建议改用 JSON 工具协议。建议只填入表单，保存后才生效。Ollama 未设置 `num_ctx` 时无法得知实际窗口，界面会提示在 Ollama 中设置。探测只访问本机管理接口，不发起生成请求；只返回数字、布尔值和固定代码，不保存或返回服务端文本。各字段按运行时公开的接口读取，缺失时少报而不报错。

宿主对每次轻量请求测量提示前缀复用：与上一次请求相比，开头有多少内容完全相同（先比较工具列表，再按顺序比较整条消息）。本地推理服务只需重新计算相同前缀之后的部分，所以这个比例越高，每一步等待越短。「本机资源」面板显示本次请求的复用比例、会话累计比例和前缀中断次数；一次请求保留的内容不到上一次的一半记为中断，例如原生工具模式下发现了新工具。会话只保存上一次请求各条消息的摘要和长度，不保存文本。该数值按发送内容计算，改动过的消息整条算作未复用，因此是下限；它不代表某个推理服务实际缓存了多少。

未显式提供 `--max-chars` 时使用 Token 预算。明确传入的字符上限继续生效；`--max-tokens`、`--steps` 和 `--max-wall-seconds` 可进一步限定本次运行。实际步骤也受供应商轻量配置约束。

超过预算时，providers 批量裁剪旧交换并保留余量，后续请求复用检查点。人类要求和当前工具交换保留，原始完整记录仍在 journal。需要旧证据时按工具回指读取。

长文件可分段调用文件工具：

```json
{"path":"result.txt","content":"第一段\n"}
{"path":"result.txt","content":"第二段\n","append":true}
```

每次仍需 path 和 content。追加不自动插入分隔符；新文件为 UTF-8，已有文件保留编码与主行尾。建议每段约 4000 字符以降低模型输出截断概率，这是指导而非强制输入上限。

planning 从“交付”“保存”“deliverables”等明确指令登记输出路径，包含代码、测试、数据与报告文件；输入和参考路径不作为交付物。用掉四分之一步骤仍没有任何输出文件时，提示开始保存可复用实现和已有发现。接近预算时提示实际缺项，若最后阶段仍缺文件，再核对一次，整轮最多三次。文件落盘不代表功能验收通过；普通对话不收到工作交付提醒。

在原生工具模式中，如果明确要求的文本报告仍不存在，最后四步内预留一个报告生成步骤，优先保存模型对实际结果、失败与未完成项的说明，然后继续原任务。报告步骤使用独立生成视图，把原任务和近期会话的有界摘录作为事实材料传入，明确标注材料不完整，原会话记录保留；此步骤只选择写文件工具，仍经过当前文件权限与审批。不增加模型请求上限、不覆盖已有报告、不替模型编造 JSON 结果或修复代码。报告生成属于 `planning.report_finish` 功能。JSON 工具协议继续使用普通收尾提醒。

轻量模式由自己的请求窗口管理历史，不叠加旧语义整理。辅助整理的内部超时记录为失败，用户主动停止仍按取消处理。模型仍可能生成错误代码、参数或不完整交付，结束状态和单次工具成功不等同于完整验收。

`planning.failure_repair` 将实际失败的工具输入和错误首尾摘录带入接下来的修复步骤，引导定位原因、修正并重跑原检查；只有原检查实际成功才记录该检查通过。最多保留四个未解决失败，修正中途的工具参数错误不会覆盖原检查失败。文件修改成功后，下一步优先复跑原检查，避免反复按旧错误重写。没有代码变化时，单个失败最多占用四步专用提示，检查耗时文字变化不会重置该窗口。用掉四分之一步骤后，宿主根据实际文件缺项指定下一份交付物。提示同时包含剩余步骤与用时。模型提前结束而仍有缺项时，最多在同一预算内继续两次，不追加轮次或提高请求上限。权限拒绝、等待审批、用户停止和插件关闭不触发自动修复；报告通常避让正在进行的修复，会参考本轮已观察到的最长模型调用耗时提前安排保存机会（基础预留为总时长15%且最多两分钟，不提高原上限）。原始记录与工具权限保留，文件存在及检查退出成功都不代表整题正确。

命令中明确引用已登记交付文件时，作为候选检查持续跟踪并要求原命令复跑。一般读取、探查及工具参数错误提供诊断；后续工具成功会退出该次操作提示，不把它算成原检查通过。这样不会因读取输入时的旧命令错误，反复要求重新修改程序。

修复指导、目标提醒和剩余预算等逐步变化的宿主指导放在请求末尾：最后一条是纯文本用户消息时接在其后，否则单独作为末尾消息。系统提示保持逐字节不变，保留原编码角色、工具和分页说明，本地推理服务可以复用已有的 KV 缓存前缀。JSON 工具协议把工具说明写在系统提示里：首次请求列出的工具保持不变，之后发现的工具附在请求末尾，到下一次裁剪历史时并入系统提示；已列出的工具被移除时立即重排，系统提示不会列出已不可用的工具。原生工具模式的工具列表由推理服务的对话模板渲染，发现新工具仍会改变前缀；普通交付缺项只补充事实，不切换全局角色。

命令解析或命令不存在等执行输入错误，不作为程序断言持续追踪；后续成功操作将其退役，记录为操作恢复，不冒充原检查通过。代码文件修改才刷新修复窗口，Markdown报告、文本说明和结果JSON写入不会触发“代码已修正，请复跑”。真实程序检查失败仍需同命令成功；验收工具的超时参数不改变检查身份。

`planning.delivery_verification` 将文件交付与模块导入分开验收。JSON交付必须能解析；明确声明可导入/模块导出或静默import的 `.mjs`、`.cjs` 交付，会在轻量模式首次具备模块文件、代码修改后，经正常 exec 权限执行 `delivery_verify`。测试文件不当作库模块导入。探针从真实 `.mjs` 消费者导入，检测提前退出、错误、超时及要求静默时的输出；CLI退出0不作为导入成功证据。默认共10秒、单模块最多5秒，未获得证据保持未通过，不增加原模型步数或用时预算。

验收结果绑定模块内容哈希和本会话实际代码修改版本。代码或依赖修改后旧结果失效，报告写入不使其失效；相同文件上的失败不因声明“完成”而消失。文件清单通过而导入未通过时不能报告交付验收通过，可在原预算内有限续作。标准模式可显式调用同一工具；没有Node导入契约的任务不自动执行模块。此检查不替代用户任务的行为测试，也不代写测试、结果JSON或修复代码。
