# 工具调用判定（决策模型）

更新于 2026-11-14。归属 `tool_judge` 插件：后端 `ts/plugins/tool_judge/src/`，宿主绑定 `ts/apps/server/src/tool-judge-host.ts`，界面 `webapp/src/plugins/tool_judge/`，目录登记见 `ts/catalog/tool_judge.json`。

## 做什么

可选的判定模型在高风险工具调用执行前看一眼，减少失败调用浪费的时间。判定模型可以是任意已保存的模型配置：本机推理服务上的小模型，或一个 API。

- **只看高风险调用**：需要审批的门类（`exec`、`write`、`edit`、`mcp`、`web_fetch`）和委派类工具（`task*`、`swarm_start`、`swarm_post`、`board_post`）。读取、glob、grep 等不判定，它们失败的代价很小。
- **每步一次请求**：同一步的所有高风险调用合并成一次判定请求。请求开头是固定的系统提示，本地推理服务可以复用缓存；其后是这些工具的说明、用户目标（截短）、最近三个工具结果和待判定的调用。
- **四种结论**：通过；建议（调用照常执行，结果里附一条提示给主模型）；修正（意图清楚但参数差一点，例如路径拼写、PowerShell 不支持的写法）；拦下（肯定失败或明显违背目标）。
- **默认只建议**（项目所有者 2026-11-14 决定）。在 设置 → 工具调用判定 里可以分别打开「修正参数后再执行」和「拦下调用一次」。
- **不是权限闸门**：权限、审批和完全访问模式都不变。修正后的调用照常经过参数校验和权限检查；被拦下的调用原样重试时一定放行（同一调用最多拦一次）。
- **失败放行**：没有选择判定模型、判定超时（默认 10 秒）、出错或答复看不懂时，调用照常执行，记录为「判定不可用」。

## 怎么生效

判定在模型答复保存之前进行，所以保存下来的步骤、权限检查和审批重放看到的都是修正后的调用；判定记录里保留原参数。工具卡片上显示判定结果（建议、已修正、已拦下、判定超时），可以展开看理由和原参数。

签名推理（某些 API 的 reasoning 签名）存在时，修正只作为建议，避免改写已签名的调用。

## 证明它有用

每个会话在 `tool_judge_stats` 里记录：判定的调用数、判定请求数与失败数、判定耗时、各结论次数、修正执行与成功次数、拦下次数、**误拦**（被拦下后原样重试并成功的调用）、以及判定通过但仍然失败的调用（其中可避免的部分）。设置页的统计卡片按 7 天、30 天或全部汇总。

2026-11-14 的实测（J2）显示：能力较强的 API 模型上，可避免的工具失败只占约 5% 的时间，逐个判定的成本可能高于收益；判定更可能对本地小模型有用。请用这些计数决定是否打开修正与拦下。

## 本地还是 API

- 判定模型和主模型在同一块 GPU、同一个推理服务上而且不是同一个模型时，服务可能来回切换模型，每次多花几秒。建议用常驻的小模型，或另一台推理服务。
- 主模型在本地、判定用 API 时，只有高风险调用的简短提示离开本机。
- 判定请求经过同一个模型准入调度：用户自己的对话按前台优先；蜂群成员按所在蜂群排队。

## 范围与限制

- 用户对话和蜂群成员（按蜂群的设置）会被判定；只读子代理和工作流角色目前不判定。
- 答复必须是 JSON 对象；看不懂的条目一律按通过处理。
- 判定看到的是简短摘要，不是完整对话，可能判断错误；所以默认只建议。
