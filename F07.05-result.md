# F07.05 Result — 深化插件组件包与生命周期 (Component Packages & Lifecycle)

- **Status**: Completed
- **Files changed this round**:
  - `ts/plugins/extensions/src/components.ts` (new): the component-package layer for data manifests. `validateComponents` accepts declarative components grouped by kind (`skills`, `commands`, `hooks`, `mcp` — anything else is an `unknown component kind` error), each entry `{ id, description?, alwaysLoad? }` with a lowercase resource id, ≤64 entries per kind and ≤200-char descriptions; duplicate `kind/id` pairs inside one manifest are rejected. `componentOwners` builds the ownership registry (one row per declared component, `kind/id` ascending, with owner, adapter, version, enabled, alwaysLoad) and reports **conflicting claims** (the same `kind/id` declared by two plugins) as a map the panel can render. `effectiveComponents` answers the gating rule: a component is registrable only when its owning package is `enabled` **and** its adapter (`builtin`) is in the effective set — a disabled or dependency-blocked plugin contributes nothing, so no new task can reach its components; `alwaysLoad` decides `loadPolicy: "always" | "on-demand"`. `uninstallPackage` removes an installed data manifest and is **refused while the package is enabled** (`disable the package before uninstalling it`), refuses unknown ids and refuses to cross a symlink. `componentsDigest` hashes the normalized component declarations so upgrades can be compared per field, and `componentOwner`/`componentSummary` serve panel queries.
  - `ts/plugins/extensions/src/catalog.ts`: `catalogItems` embeds a `components` summary per row (`total`, `byKind`, `alwaysLoad` keys, conflicting keys), so the plugin panel answers "which components live in this plugin" without a second round trip.
  - `ts/plugins/extensions/src/marketplace.ts`: new `POST /api/plugins/marketplace/:id/uninstall` route — delegates to `uninstallPackage`, returns 400 with the refusal reason or 200 with `{ ok, removed }` plus the refreshed marketplace listing.
  - `ts/plugins/extensions/src/index.ts`: exports the component-package API (`COMPONENT_KINDS`, `componentOwner(s)`, `componentSummary`, `componentsDigest`, `effectiveComponents`, `uninstallPackage` and their types) and registers the uninstall route string in `EXTENSIONS_ROUTES`.
  - `ts/plugins/extensions/src/validate.ts`: the inline manifest audit now validates `components` (`invalid_component` issues) and the SDK-owned `settings`/`events` contract fields (`invalid_contract` issues, implemented in `contribution.ts` per F07.06); `MANIFEST_FIELDS` admits the three new keys, and `BUILD_ONLY` now aliases `BUILD_ONLY_FIELDS` from `contribution.ts` so build-only powers stay defined exactly once.
  - `ts/plugins/extensions/test/component-packages.test.ts` (new, 7 tests).
- **Contract invariants satisfied**:
  - **Component ownership is queryable in the plugin panel**: catalog rows carry the component summary; `componentOwners`/`componentOwner` map every component back to its owning plugin, and duplicate claims surface as conflicts.
  - **Disabled plugins get no new tasks**: `effectiveComponents` yields nothing unless the owner is enabled *and* its adapter is effective (native `native_ops`/`batch_calls` defaults untouched — no adapter set is changed by this round).
  - **Optional plugins never auto-install**: the marketplace listing alone writes no manifest; `installedVersion` stays `null` for optional entries until an explicit `install` (pinned by the final test).
  - **Lifecycle is ordered**: install is forced-disabled, upgrade is version-compared with `alwaysLoad` stable across versions, and uninstall is refused while enabled — enforced both at the API layer and the route.
  - Components remain pure data: entries only name and describe; nothing is imported or executed by this layer.
