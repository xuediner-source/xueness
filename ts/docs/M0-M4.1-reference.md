# Xueness TypeScript 后端（strangler 迁移工作区）

这里是 Xueness 后端从 Python 迁到 TypeScript 的工作区。迁移方式是 **strangler**：
TypeScript「前门」(front door) 站在 Python 后端前面，已迁完的路由由 TS 自己回答，
其余请求原样转发给 Python。Python 实现在迁移期间就是**行为基准**：每个移植过来的
模块都和 Python 跑差分测试，结果一致才算完成。

路线图（Notion）：「Xueness 后端迁移 TypeScript 路线图」，里程碑 M0–M6。

## 快速开始

需要 Node ≥ 24.11（直接运行 `.ts`，不经过构建）。差分测试还需要 Python ≥ 3.11
（`python3`，或用 `XUENESS_PYTHON` 指定），只用标准库（在没有第三方包的 venv 里验证过）。
另外需要仓库根目录下的 `xueness/` 和构建好的 `webapp/dist/`（`npm --prefix webapp run build`）。

```bash
cd ts
npm install
npm run check        # 行数上限 + 插件门禁 + 类型检查 + 全部测试（本机结果见 HANDOVER 第 8 节）
npm run serve        # 前门 + 受管 Python 后端，默认 http://127.0.0.1:8137
```

Windows PowerShell 运行差分测试前，确认选中的是 Python 3.11 以上版本。例如装有
Python Launcher 时，可运行以下命令；这样不会误用 PATH 上的 Python 3.10 而跳过差分测试：

```powershell
$env:XUENESS_PYTHON = (py -3.11 -c "import sys; print(sys.executable)").Trim()
npm.cmd run test:sessions
```

参数（`npm run serve -- --help` 可查看）：`--port`、`--host`、`--project-root`、`--python`、
`--state`、`--web-runs`、`--workspace-root`（可重复），以及 `--backend-port N`
（接一个已经在跑的 Python 后端，不再自己启动）。非 loopback 地址仍然要求
`XUENESS_ALLOW_REMOTE=1`，规则和 `web.py` 的 `resolve_bind_host` 一致。

| 命令 | 作用 |
| --- | --- |
| `npm test` | 全部测试（含 Python 差分） |
| `npm run test:sessions` | 会话存储、修订日志、跨进程锁及会话投影的 Python 差分测试 |
| `npm run test:fast` | 跳过需要 Python 的测试（`XUENESS_SKIP_PYTHON_TESTS=1`） |
| `npm run typecheck` | `tsc` 严格模式，只做检查，不产出文件 |
| `npm run check:lines` | 任一 `.ts` 文件超过 400 行就失败（`XUENESS_MAX_LINES` 可调） |
| `npm run check:plugins` | 插件静态门禁：manifest、白名单、import 与声明的能力是否一致（规则见 `scripts/plugin-gate.ts`） |
| `npm run bench:tools` | Xueness-bench 工具基准：在生成的同一个工作区上跑 P0 检查和各工具耗时，TS 与 Python 对照（`--files`、`--deps`、`--iterations`、`--no-python`、`--json`） |
| `python3 ts/test-support/python/run_via_front_door.py` | 在仓库根目录执行：Python 的 HTTP 级测试全部经前门跑一遍（约 6 分钟） |

加大差分规模：`XUENESS_DIFF_CASES`（事件会话，默认 3000）、`XUENESS_IGNORE_CASES`
（随机 git 仓库，默认 150）、`XUENESS_GUARD_CASES`（Host/Origin 值，默认 4000）。

## 已完成内容与验证方式

**contracts**（43 个测试）：events v1 的校验和派生，与 Python 跑差分。默认 3,000 个随机会话，
另手动验证过 40,000 个，输出逐字节一致。另有插件 manifest v2、能力声明、catalog 规则和 v1 升级（见下），
以及 M4.1 用到的 Python 兼容层（见「M4.1」一节）。

**kernel**（33 个测试）：插件生命周期、scope 的资源回收顺序、服务注册，M2 的能力守卫、
受限上下文、插件宿主和热启停泄漏测试（见下），以及 M3 的工具事件和工具租约（见「M3」一节）。

**插件 manifest v2 与热启停**（M2 退出标准）：

- 契约（`packages/contracts`）：`plugin-manifest.ts` 校验 apiVersion 2，未知字段报错，
  `entrypoint` / `command` 这类外部代码入口一律拒绝（要单独审计）。`tools` 写明 Gate 类型和
  `mutating` / `concurrencySafe`。`config` 是 JSON Schema 子集，默认值必须能通过它自己的 schema。
  `plugin-capabilities.ts` 定义能力：`fs.read` / `fs.write` 按根目录（workspace、state、temp、home、any），
  `net.connect` 按主机模式和端口，`net.listen` 分 loopback / any，`exec` 按程序名，`secrets` 按名称前缀。
  写隐含读。`plugin-catalog.ts` 检查跨插件规则：服务、路由族、命令、资源、前端和桌面模块、
  工具名（包括 `mcp__*` 这样的族）都只能有一个归属，依赖必须存在，不能成环。
- v1 兼容：30 个 Python v1 manifest 都能升级成合法的 v2，字段不丢，catalog 没有冲突，
  路由族归属和 v1 完全相同。工具的 Gate 类型和标志取自 Python 工具注册表（差分对照）。
  只有 `mcp__*`、`skill_read`、`task` 三个由 Python 核心定义，没有对照来源，升级时按最保守的
  方式处理（gate 记为 `unknown`，视为会修改文件）。
- 运行时（`packages/kernel`）：`capability-guard.ts` 按授权检查路径、程序、连接、监听和密钥。
  路径会先解析符号链接，不能借链接逃出根目录。守卫只能收窄，不能放宽。`Context.restrict()`
  生成插件用的受限上下文：只能 provide / get manifest 声明的服务；只能注册声明过的工具，
  Gate 类型和标志必须一致，工具的 `requires` 必须在授权范围内；不能伪造 `internal/*` 事件。
  `ctx.spawn / serve / fetch / subscribe / secret` 先过守卫，再挂到插件的作用域上。子进程在独立
  进程组里，停用时先 SIGTERM，宽限期后 SIGKILL，再清掉组里残留的后台孙进程。服务器关闭时
  断开所有连接。请求随作用域中止，重定向不自动跟随，每一跳都要重新过守卫。
- 插件宿主（`plugin-host.ts`）按 manifest 加载内置插件。授权（默认等于声明）覆盖不了声明的能力时，
  状态是 `blocked`，并列出缺少哪些。依赖的插件没启用也是 `blocked`。运行中可以
  `enable / disable / configure / setGrant`。停用时先撤下 `plugin.<id>` 标记，让依赖它的插件在它的
  服务还可用时先停，然后再释放它自己；重新启用后，依赖方自动恢复。配置按 schema 校验，
  不合法直接拒绝，合法就重启插件。激活卡住时最多等 `settleTimeoutMs`（默认 10 秒），停用照常
  进行，之后 apply 再申请资源会被拒绝。
- 退出标准测试（`packages/kernel/test/plugin-hot-reload.test.ts`）：测试插件申请了 timeout、interval、
  总线监听、外部 emitter 监听、服务、工具、一个 loopback HTTP 服务器加一个没结束的请求、
  一个带后台孙进程的 `sh` 进程组和一个 node 子进程。启停 3 轮，每轮停用后
  `process.getActiveResourcesInfo()` 都和基线逐项相同，总线监听数、服务、工具、emitter 监听数
  也回到基线，所有 pid（包括孙进程）都已结束；依赖方每轮都恢复（activations 依次是 1、2、3）。
  另外两项：激活到一半抛错，已申请的资源全部回滚；激活卡住也能停用，不泄漏。做过变异验证：
  去掉进程组清理，或者去掉 `clearInterval`，测试都会失败。
- 内置 TS 插件：`plugins/files`（read list glob grep write edit，需要 `fs.write: workspace`）和
  `plugins/shell`（exec，需要 `exec: *`、`fs.write: workspace, state`；配置项 defaultTimeoutMs /
  maxCaptureBytes / scrubEnv / passEnv，改配置就重启插件生效）。白名单在
  `apps/server/src/bundled-plugins.ts`。测试确认注册的工具和 manifest 声明完全一致，Gate 类型和
  标志也和 Python 注册表相同。
- 静态门禁（`npm run check:plugins`，用 TypeScript 编译器解析源码）：manifest 合法，id 和目录名相同；
  白名单和目录一致；源码只能 import Node 内置模块、`@xueness/contracts / kernel / engine-tools`
  和插件自己的文件；`child_process` 等需要 exec，`net / http / https / tls / dns` 和全局
  `fetch / WebSocket` 需要 net，`fs` 和文件工具需要 fs；禁止 `eval`、`Function`、`require`、`node:vm`、
  `process.binding` 和动态计算出来的 `import()`。

**engine-tools**（48 个测试），修掉了评审时提出的 P0 问题：
- 编码：UTF-8 / GBK / GB18030 自动识别。GBK 全部 21,000 多个字符、GB18030 样本都与 Python
  编解码逐字节一致。写回时保留原编码和原换行（不再把 CRLF 改成 LF）。
- 忽略规则：`.gitignore`、`.ignore`、`.git/info/exclude`，以及上层目录直到仓库根的 `.gitignore`。
  和 `git ls-files --others --exclude-standard` 做差分：默认 150 个随机仓库，验证过 2,000 个，结果一致。
  `.git` 等版本库目录始终跳过，`node_modules`、`.venv` 等默认跳过，不跟随指向目录的符号链接。
- glob / grep：BFS 用索引推进，不再 `pop(0)`。按修改时间从新到旧排序；有分页、上下文、
  多行模式，并兼容 Python 风格正则（`(?P<name>)`、`\A`、`\Z`）。跳过二进制文件和超过 4 MB 的文件。
- exec：默认超时 120 秒，最长 600 秒，超时后杀掉整个进程树（包括 trap 了 TERM 的进程）。
  输出保留头尾各 24 KiB，完整输出另存到工作区之外。区分 `command_not_found`、`command_failed`、
  `command_timeout` 等错误码，失败不再结束整个 run。环境变量里 KEY/TOKEN/SECRET 一类会被清掉。
  `artifactsDir` 不允许放在工作区里面。后台任务见下一节。

**M3：工具执行链路**（engine-tools 后台任务 7 个测试、permissions 24 个、tool-bridge 20 个、
kernel 工具事件与租约 5 个、基准 2 个）：

- exec 后台任务（`engine-tools/src/background.ts`、`exec-tasks.ts`）：`exec` 带 `background: true` 时立刻
  返回任务 id；之后用 `exec_output` 读输出（可以先等它结束，最多 600 秒；不给 id 就列出本会话的任务），
  用 `exec_kill` 停止。任务在独立进程组里运行，stdin 关闭。stdout / stderr 完整写进工作区之外的
  日志文件（每个最多 64 MiB），还没读过的输出在内存里保留头尾（每路 24 KiB），所以每次只返回上次
  之后的新输出，大小有上限。默认超时 30 分钟，最长 24 小时；超时和 `exec_kill` 都杀掉整个进程树。
  同时最多运行 8 个（shell 插件配置 `maxBackgroundTasks`），结束的任务保留最近 32 个。任务只有启动它的
  会话看得到。任务管理器挂在 shell 插件的作用域上：停用或改配置时任务全部停止，比主进程活得久的
  子进程也一样。前台命令的超时仍然最多 600 秒，更长的必须放到后台。
- 权限策略（`packages/permissions`）：以 Python 的 WebGate 为基准。审批类工具（write、edit、exec、mcp、
  web_fetch、web_search）默认要询问；一次性批准绑定工具调用 id 和完整的 subject；有 build / edit / yolo /
  plan 四种模式；未知的 Gate 类型一律拒绝。差分测试把模式、类型、批准和禁用列表的所有组合拿去和
  Python 对照，结论（允许 / 询问 / 拒绝）全部一致。在这个基础上增加了三项：
  - 规则：`allow` / `deny` / `ask` 三组，写法是 `工具` 或 `工具(说明符)`。工具可以写名字、Gate 类型、
    族（`mcp__*`）或前缀。命令按词匹配，`git log:*` 和 `git log *` 都是按词边界的前缀；路径是工作区
    相对的 glob；web 类按文本或 `domain:主机名`。判定顺序固定：未知类型 → 禁用 → deny 规则 →
    plan 模式 → ask 规则 → 远程 SSH exec（总要一次性批准，yolo 也一样）→ 不需要询问的类型 →
    allow 规则 / 会话规则 / 只读命令 → 模式 → 一次性批准 → 询问。deny 和 ask 规则检查一行里所有
    可能运行的命令，包括 `sh -c` 和 `$(…)` 里面的，以及被 `timeout` / `nice` / `nohup` 等包起来的。
  - 只读命令自动放行（`shell-parse.ts`、`readonly.ts`）：自带的 shell 解析器把命令行拆成简单命令，
    识别引号、管道、`&&` / `||` / `;`、重定向、变量赋值、命令替换和 `sh -c`，并记下所有看不懂的结构。
    整行都解析成功，每个简单命令都只读（`ls`、`cat`、`grep`、`rg`、`git log / diff / status` 等；`sed`
    只认不写文件的脚本，`find` 不能带 `-exec` / `-delete`），没有变量赋值和写文件的重定向，也不涉及
    工作区外的路径，才会自动放行。
  - 会话内「总是允许」：询问时附上建议规则，一条只放行这一次的调用（如 `exec(npm test)`），一条放宽
    （如 `exec(npm test *)`、`edit(src/**)`、`web_fetch(domain:example.com)`）。用户选了就记在这个会话里，
    可以导出快照再恢复。审计记录保留最近 200 条，会话规则最多 1,000 条。
- 工具事件（`kernel/src/tool-events.ts`）：`before_tool_execution`、`before_tool_effect`、
  `after_tool_authorization`、`after_tool_execution`。插件只能订阅 manifest `toolEvents` 里声明过的事件，
  `before_tool_effect` 和 `after_tool_authorization` 没声明就订阅不了。派发顺序和 Python 的
  `tool_event_order` 相同：先依赖，再优先级，再订阅顺序。只有内核能派发。派发器
  （`tool-bridge/src/dispatch.ts`）给每个回调 10 秒；声明过的 deny 才生效（带原因，最多 500 字符），
  没声明的 deny 被忽略；观察者抛错或超时不影响调用；严格的 `before_tool_effect` 策略抛错、超时或返回
  不合法的结果时，调用以 `tool_policy_unavailable` 拒绝。`after_tool_execution` 的改写必须保持 `ok`
  和结果结构不变，否则丢弃。回调拿到的是冻结的快照。以上情况都记为诊断，保留最近 50 条。
- 工具租约（`kernel/src/tool-registry.ts`）：每次调用都持有工具的租约。插件停用时先中止它正在执行的
  调用（中止信号传进工具，exec 会杀掉整个进程树），最多等 10 秒，然后照常卸载；之后再调用得到
  `unknown_tool`，重新启用后恢复。插件拿到的工具视图只有声明，拿不到别的插件的实现。
- 工具桥（`packages/tool-bridge`）：`ToolBridge.call()` 固定按这个顺序执行：取租约 → 校验输入、算出
  subject → `before_tool_execution` → 权限判定（需要询问时交给 approver：允许一次、本会话总是允许或
  拒绝；没有 approver 就返回 `approval_required`，带上 subject 和建议规则）→ `before_tool_effect` →
  `after_tool_authorization` → 运行工具（租约、本次调用、运行环境三方的中止信号合在一起）→ 释放租约 →
  `after_tool_execution`。被拒绝的调用返回 `permission_denied` 或 `plan_mode_denied`，碰不到工具。
  plan 模式下除了只读操作，只能写本会话的计划草稿（草稿在工作区之外，也可以读；草稿或它所在的目录
  是符号链接时拒绝）。
  `callAll()` 按顺序执行一轮里的调用，相邻的 `concurrencySafe` 调用并发执行（最多 10 个）。
  做过变异验证：去掉 deny 的声明检查、跳过 `before_tool_effect`、没有 approver 时直接放行、不把租约的
  中止信号传给工具、不限定计划草稿目录、把没冻结的结果交给改写回调，6 处改动都会被测试发现。
- 退出标准测试（`tool-bridge/test/p0-regressions.test.ts`）：加载真实的 files 和 shell 插件，经工具桥
  逐条验证评审时的 P0 问题：CRLF 经过 read / edit / write 仍是 CRLF；GBK 文件能读、能 grep，edit 后仍按
  GBK 写回；grep 和 glob 不进 `node_modules`，也不出被忽略的文件；不存在的命令返回 `command_not_found`，
  同一轮后面的调用照常执行；超时允许时命令能跑过 30 秒（用 mock 时钟推进 31 秒，对照组设 30 秒超时，
  得到 `command_timeout`）。
- Xueness-bench（`npm run bench:tools`）：生成同一个工作区（默认 2,000 个源文件加 4,000 个
  `node_modules` 文件，约 4 MB），TS 经工具桥运行，Python 直接调用 `builtin_tools` 和 shell 的处理函数。
  下面是一次 9 轮取中位数的结果（Node 24.14、Python 3.13、Linux x64；这台机器上多次运行的耗时
  会相差 30% 左右）：

  | 项目 | TS | Python |
  | --- | --- | --- |
  | edit 保留 CRLF | 通过 | 失败：改写成 LF |
  | read GBK 文件 | 通过 | 失败：UnicodeDecodeError |
  | grep 跳过 node_modules 和 .gitignore | 通过 | 失败：100 条结果里 40 条来自 node_modules、20 条是被忽略的文件 |

**M4.1：provider 适配器**（`packages/providers`，150 个测试：HTTP 差分 118 个、辅助函数差分 12 族、本地 20 个）：

- 范围：`OpenAICompatible`（chat completions，流式和非流式、tool calls、usage、lightweight 运行档）和
  `AnthropicMessages`（Messages API，tool_use 归一化），以 `provider.py` 为准：请求体逐字节一致，重试和退避、
  `Retry-After`（最多睡 2 秒）、运行截止时间（同时约束请求头、响应体和退避）、错误分类（HTTP 状态 / 传输 /
  协议 / 回调 / 用户停止）以及脱敏后的错误信息都相同。流里已经交出过 delta 之后断开，不再重试，调用方
  不会看到重放的前缀。一起移植的还有 `tool_protocol.py`、`runtime_options.py`、`lightweight_config.py`、
  `response_metadata.py`，以及多模态附件信封（严格 base64、文件签名、单次请求预算）。`_media_refs` 只能经
  调用时传入的媒体绑定解析（M4.3 接 MediaArtifactStore）。
- HTTP 客户端（`http.ts`、`idle.ts`、`proxy.ts`）按 urllib 的语义实现：不跟随重定向，不压缩，不 keep-alive。
  失败按 Python 的异常族分类：请求发完之前是 `URLError`，之后是 `TimeoutError`、`ConnectionResetError` 等。
  EOF 分隔的响应体被 RST 截断时报 `ConnectionResetError`（Node 的解析器会当成正常结束）。超时和 Python 的
  socket timeout 一致：连接、TLS 握手、整个请求的发送（`sendall`，有进度也不续期）各算一个超时窗口，读取时
  每次等数据算一个窗口，调用方处理已缓冲数据的时间不算。请求发完之前不读响应：服务器提前回 413 并断开时，
  和 urllib 一样得到 `URLError`。计时用 `performance.now()`，不会提前触发。远程 HTTPS 按环境变量
  （`https_proxy` / `no_proxy`，小写优先）走代理时建立 CONNECT 隧道，代理凭据只出现在隧道请求上。
- HTTP 差分（`provider-differential.test.ts`，oracle 是 `test-support/python/provider_oracle.py`）：TS 和 Python 的
  适配器连同一个脚本化的 HTTP 服务器，比较发出的请求（方法、路径、请求体、主要请求头）、结果、错误

  Anthropic 流式 17、非流式 22、请求体 13、构造与校验 27，覆盖畸形 SSE、截断、重置、超时、截止时间、
  配额和上下文溢出的错误码、各种 `Retry-After`、回调抛错和停止。辅助函数差分（`provider_units_oracle.py`）
  12 族约 600 个输入：base64、Retry-After、URL 拆分、loopback 字面量、lightweight 选项、有效选项、兼容性
  选项、运行时选项、原生 tool call 归一化、信封文本、严格 JSON、usage。
- 本地测试（不需要 Python）：取消、真实时钟上的截止时间（所有定时器都提前 30 ms 触发，也不会提前超时）、
  RST、分段到达的配额错误体、媒体绑定、Anthropic 请求头；`http-idle.test.ts` 6 个（握手卡住、上传卡住、
  上传有进度也不续期、上传期间到达的数据不续期、提前到达的响应、调用方耗时不计）；`http-tunnel.test.ts`
  5 个（经隧道的完整 HTTPS 交换、所有请求共用一个 TLS 上下文、CONNECT 与 407、代理不回应、隧道内握手超时）。这些时序上的期望都先在
  Python 上实测过。做过变异验证：空闲计时器或截止时间定时器不复核到点时间、不延后提前到达的响应、把失败的
  最后一次写当成发送完成、把调用方耗时算进超时、上传期间收到数据就续期、每个请求重新传 `ca`，7 处改动都会被
  测试发现。
- contracts 新增 `py-json.ts`（CPython 的 `json.loads`：重复键、NaN、错误位置）、`py-codecs.ts`（严格 UTF-8、
  `json.detect_encoding`）、`py-ops.ts`（Python 的下标、`.get`、`+` 和迭代，失败时抛同样的异常类型，
  畸形响应因此落进同样的错误分类）。
- 移植中发现并修掉的问题：截止时间的定时器会早 1–2 ms 触发，多出一次重试 sleep（两个差分用例大约每 6 次
  失败 1 次），`SYSTEM_CLOCK.sleep` 也会早醒；Node 自带的 socket 空闲计时按整毫秒算、会提前触发，异步写之后
  会跳过一个周期（握手或上传卡住要等 2 倍超时），调用方忙的时候也在计时，所以换成了自己的计时器；
  最初把上传进度当成活动，比 Python 宽松（Python 3.5 起 `sendall` 整体只有一个超时窗口），已改；
  上传途中到达的响应 Node 会先交出来，连接被重置时还会把失败的最后一次写报成完成，持有响应时被中止的请求
  会挂住；走代理的 HTTPS 绕过了 CONNECT 隧道（`agent: false` 时 Node 忽略 `createConnection`）；
  `Host` 头多了 `:443`；每个 HTTPS 请求都重新解析全部根证书（约 25 ms，阻塞事件循环），改成进程内共用一个
  TLS 上下文；binascii 在 3.13 的报错信息；`float()` / `int()` 接受 Unicode 数字（如 `١`、`２`）。

**apps/server 前门**（29 个测试，其中 3 个是内置插件白名单）：
- 守卫（Host、Origin、Sec-Fetch-Site、CSRF、桌面 token）是 `web.py` 的移植，
  差分验证了 200,000 个生成的 Host/Origin 值，结果一致。
- HTTP 差分：同一批原始字节分别直接发给 Python 和发给前门，比较状态码、除 Date/Server
  外的全部响应头、响应体，以及连接是否被关闭，都必须一致。覆盖 UI 资源、越权访问、
  请求分帧、CSRF、`Expect: 100-continue`、HTTP/1.0 与 2.0，以及多请求共用一条 keep-alive 连接。
- 请求头拒绝按 Python 的顺序由前门自己回答：请求行超过 64 KiB（414）、HTTP/2.0 及以上（505）、
  头部行数超过 Python 上限或单行超过 64 KiB（431）、`HEAD`（501，响应体照 Python 一样发出）。
  Node 解析器拒掉的分帧错误（`Content-Length: 1,2`、重复或为空的长度、和 `Transfer-Encoding`
  同时出现、非法的 `Transfer-Encoding`）给出和 Python 相同的 400 `invalid_content_length`
  或 411 `length_required`。这些都在 HTTP 差分里逐条对照过。
- 请求头时限：对应 `_HEADER_IDLE_SECONDS`（15 秒）和 `_HEADER_DEADLINE_SECONDS`（20 秒）。
  什么都没发的连接到时直接关闭、不回应；已经开始发请求头的回 408 `request_timeout`
  （和 Python 一样不带 `Connection: close` 行）；keep-alive 连接等下一个请求同样按这个时限。
  请求体不在前门计时，由 Python 自己的 `_BODY_*` 时限负责。时限、桌面 token、静态资源目录
  都可以用 `configure()` 在运行中修改。
- 代理设计：每条客户端连接配对一条专属上游连接。Python 决定关连接时（不论有没有
  `Connection: close`），客户端连接在拿到应答后也会关闭。空闲的上游连接在 10 秒时由前门回收，
  早于 Python 的 15 秒，所以 Python 的空闲关闭不会传到客户端。请求头立刻发给上游，
  Python 可以在收到请求体之前就拒绝（403/413）。
- 长轮询与流式：用脚本化的上游验证过，长轮询超过上游空闲回收时间也能完整返回，
  event-stream 是边产生边送达的，几个并发长轮询之间互不阻塞。
- 受管 Python：通过一个 bootstrap 启动 `xueness.web`，它会监听 stdin。前门不管怎么退出
  （包括 SIGKILL、崩溃），Python 都会走 KeyboardInterrupt 正常关闭，不会变成孤儿进程。
  Windows 上通过关闭 stdin 优雅停止，不用 TerminateProcess。POSIX 上 Python 在独立的进程组里：
  终端按 Ctrl-C 只会送到前门，由前门向 Python 发一次 SIGINT；超时兜底时 SIGKILL 整个进程组。

## 与 Python 的已知差异（有意为之或尚未覆盖）

- 字体 MIME：前门用固定表（`font/woff2` 等）。Python 走 `mimetypes`，结果依赖主机，
  有些机器上会给 `application/octet-stream`。
- 罕见的 HTTP 版本（`HTTP/1.2`、`HTTP/1.01`）和部分畸形请求行，在到达 Python 之前就被
  Node 的解析器（llhttp）拒绝了，状态码可能不同。`HTTP/2.0` 的处理和 Python 一致（505）。
- TS 自己回答的路由，`Server` 头是 `XuenessWeb/0.1 (front door)`。
- 请求头时限：请求行还没发完就停住的连接，Python 静默关闭，前门回 408（前门看不到行边界）。
  keep-alive 连接上的下一个请求，前门从它的第一个字节开始算 20 秒，Python 从上一个应答结束开始算。
- 分帧错误如果同时缺 CSRF：Python 先检查 CSRF，回 403；Node 解析器在前门更早拒绝，回 400/411。
- 状态码的原因短语用的是 Node 的表。Python 3.12 里个别短语不同（例如 413、414），状态码和响应体一致。
- JS 的数字区分不了 `1` 和 `1.0`。契约层只在已知字段上还原 Python 的 `json.dumps` 输出。
- v1 manifest 的 `capabilities` 只是说明性的，而且普遍少写：`network`、`bots`、`browser`、`updates`、
  `remote` 等都没有声明任何能力。升级出来的 v2 会照样继承。每个插件迁到 TS 时，要在它的 v2
  manifest 里写清真实需要的能力，门禁会按代码实际 import 的模块检查。
- exec：Python 只接受 `argv`，权限 subject 是 argv 的 JSON，超时固定 30 秒，输出截到 12,000 字符。
  TS 同时接受 `command`（经 shell）和 `argv`，subject 是命令行文本（argv 按 shell 规则加引号拼成一行），
  所以两边的一次性批准不能互通。
- 文件类工具的 subject：Python 用模型给的原始路径，TS 用规范化后的工作区相对路径（`./src/a.ts` 和
  `src/a.ts` 是同一个 subject），路径规则也按它匹配。
- 工具事件：回调拿到的负载带 `owner`，不带 Python 里的 session / store 对象；回调之间不做全局串行。
  输入在 `before_tool_execution` 之前就按 schema 校验并算出 subject；不合法的调用在事件里 subject 为
  null，之后直接返回 `invalid_argument`，不进入权限判定。
- provider 错误体：Python 的 `_http_error_metadata` 只做一次 `read1`，错误体分段到达时可能读不到错误码
  （例如 429 的 `insufficient_quota` 被当成普通 429 去重试）；TS 在同样的 0.25 秒预算里等完整的错误体。
- 截止时间到点时报告的异常类型取决于当时卡在哪一步，两边都有时序依赖，差分里这类用例只比较分类和
  sleep 次数。DNS 解析的时间算进连接的超时窗口（Python 的 `getaddrinfo` 不受 timeout 约束）。
- 代理只读环境变量，不读 Windows 注册表和 macOS 的系统代理；CONNECT 的主机名不做 IDNA 编码。
  `User-Agent` 是 `Xueness-TS`（Python 是 `Python-urllib/3.x`，差分不比较这个头）。
- Python 兼容层：`json.loads` 的数字变成 JS 数字（超过 2^53 的整数丢精度，`1.0` 读成 `1`）；`str.casefold`
  是近似实现（先转大写再转小写）；少数传输错误的异常名是按 errno 推断的近似值。

- 会话存储（M4.2a）的差异，包括发现的一个 Python 修订链 bug，见 `HANDOVER.md` 第 6 节。

## 还没做

- 安装包里还没有前门：需要先把 TS 构建成 JS，并放进 electron-builder 的 extraResources，
  然后才能默认打开桌面开关（M5）。
- provider 适配器已经移植（M4.1），但还没有接进前门。会话存储层已移植到 `packages/sessions`（M4.2a，差分测试已补齐，还没接进前门）；agent loop 和 compaction
  仍在 Python 一侧（M4.2b）；sessions 路由、媒体绑定（MediaArtifactStore）和 providers 路由（连接测试、兼容性测试、模型发现）
  在 M4.3 切到 TS。工具桥已经能完整执行一次工具调用，但前门进程还没有加载 PluginHost 和工具桥，Python 的
  agent 循环也不经过它们（M4.2 把循环搬到 TS 时接上）。审批目前是
  `approver` 回调或 `approval_required` 结果，还没接到 Web UI 的审批流程。
- Windows：sessions 的真实跨进程锁和并发更新已实测，原包全量检查在本机仍有既有失败（见 `HANDOVER.md`）。
  热启停测试里进程组那部分、后台任务和插件停用时中止调用的测试，此前只在 POSIX 上验证通过；本次不宣称这些能力已在 Windows 验收。
- 插件和内核在同一个进程里，不是沙箱。守卫管的是内核提供的能力，门禁管的是源码直接 import 的
  模块。插件如果直接用 `node:fs`，门禁只能确认它声明了 fs，没法检查具体路径（要用 `ctx.guard.path`
  解析）。`net.connect` 按主机名检查，不防 DNS rebinding。
- 权限策略的边界（它决定要不要问，不是沙箱）：
  - exec 的 deny 规则只能尽力而为：脚本文件、`python -c`、`node -e`、shell 别名和函数里实际运行的命令
    都看不到。要可靠地禁止某些命令，得靠沙箱。
  - 「只读」的 git 命令也可能执行代码：仓库配置里的 `core.fsmonitor`、diff / textconv 驱动、pager 等。
    只读分类信任工作区自己的 git 配置。
  - 工作区里指向外面的符号链接，只读分类看不出来（文件工具会解析链接，不受影响），所以
    `cat 链接/文件` 会被当成只读。
  - 只读分类按 POSIX shell 语法；Windows 上的 PowerShell / cmd 没有单独分类，也还没验证过。
  - 路径规则只管文件工具：`deny read(secrets/**)` 拦不住对上级目录的 grep，也拦不住 `exec cat secrets/x`。
  - `git log:*` 和 `git log *` 都是按词边界的前缀：匹配 `git log` 和 `git log --oneline`，不匹配 `git logx`。
- 后台任务不跨重启：插件或进程重启后任务全部停止；进程异常退出时留下的日志文件，下次启动不会自动清理。
