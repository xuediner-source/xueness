## What the round proves

Acceptance for H08.01 — "the extensions path can load harness contributions" — is covered by one marketplace story end to end:

1. A data-only marketplace package is installed through the extensions resource route the `extensions` plugin mounts (`POST /api/resources/plugins` via `resourceDispatch`, the exact dispatch `createExtensionsHttp` forwards to), and read back with `loadDataManifests` from `@xueness/plugin-extensions`.
2. The harness source directory ships under the same extensions path (`<state>/resources/plugins/critic-solver/` with `deepseek-harness.json` plus its skill file), and the `deepseek_harness` RPC (`createHarnessApi` → `deepseek_harness/load`) hot-loads it.
3. Every declared contribution is indexed under `${kind}:${name}` (`tools:critique`, `hooks:after_tool_execution:critic.on_tool`, `verifiers:tests-pass`, `skills:repo-map`, `promptTemplates:solver-system`), surfaced by `deepseek_harness/list`, and fully green in `deepseek_harness/verify` (`sdk_supported`, `source_present`, `manifest_current`, `contributions_resolved`).
4. Package-kind sources (`package.json` + `xuenessHarness` block) load from the extensions path as `kind: "package"` with their own contribution names.
5. The installed data-manifest *file* is refused as a harness source (`not_a_directory`) — data manifests and harness source directories stay distinct shapes.
6. A rival extensions-path harness repeating a contributed tool is refused (`mount_refused`) and the registry is unchanged (atomic mount).
7. Hot upgrade works: `unload` frees every contribution (`ownerOf` → null), a rewritten manifest reloads at the new version.
8. Integrity refusals stay structured: a symlinked manifest is `symlink_refused`; a wrong `sdkApiVersion` is `invalid_manifest` with the `/sdkApiVersion` issue path on the loader result.

## Contract invariants satisfied

- Declarative-only on both sides: the extensions gate (`contributionIssues`) rejects packages reaching for build-manifest powers (`features`), and the harness loader never imports or executes anything from a source; the E2E asserts both.
- Loader all-or-nothing semantics: a refused mount (duplicate harness id or contribution conflict) leaves the registry exactly as it was.
- Registry ownership: every contribution key has exactly one owning harness; unmount releases all of them.
- Bounded reads: manifest size/symlink rules enforced before parsing (`symlink_refused`, structured issues).
