# F07.06 Result — 完善插件 SDK 与贡献契约 (Plugin SDK & Contribution Contract)

- **Status**: Completed
- **Files changed this round**:
  - `ts/plugins/extensions/src/contribution.ts` (new): the public SDK surface for data packages. `SDK_API_VERSION` pins the current API line and `compatVerdict` decides host/package fit by rule — one major line at a time: equal → `exact`, older package → `legacy` compatibility mode, newer package → refused `package-newer`, non-positive/non-integer → `invalid`. Public types `SettingDeclaration`, `EventDeclaration`, `PluginPackageDocument`, `SdkCompatibility` make every field a package may declare typed and declarative. `validateContributionFields` audits the SDK-owned fields: settings (types `string|number|boolean|enum`, 1–64-char titles, ≤200-char descriptions, unique non-empty enum options, ≤32 settings) and events (dot-separated lowercase names, each **namespaced under the package's own id** (`example-greeter.*` for `xueness-example-greeter`), required descriptions, no duplicates, ≤32). `contributionIssues` is the standalone pre-submission checklist: manifest shape, the build-only rule (`features`, `frontendModules`, `panels`, `defaultEnabled` are powers of trusted build manifests — a marketplace package cannot mount frontend or set defaults), compatibility, self-dependency, and the SDK field audits. `describePackage` normalizes any conforming document into the docs/panel summary, and `EXAMPLE_PACKAGE` ships a complete, isolated example plugin (one package; `skills`/`commands`/`hooks` components; the `command` capability; an enum setting; a namespaced event).
  - `ts/plugins/extensions/src/validate.ts`: wires the contract into the inline manifest audit — `settings`/`events` violations surface as `invalid_contract` issues, and `BUILD_ONLY` now aliases `BUILD_ONLY_FIELDS` from `contribution.ts` (shared wiring, credited to F07.05's diff for `components`).
  - `ts/plugins/extensions/src/index.ts`: exports the SDK API (`EXAMPLE_PACKAGE`, `SDK_API_VERSION`, `compatVerdict`, `contributionIssues`, `describePackage`, `validateContributionFields` and their types).
  - `ts/plugins/extensions/test/plugin-sdk-contract.test.ts` (new, 4 tests).
- **Contract invariants satisfied**:
  - **Public types**: every declarable field (`components`, `settings`, `events`, `dependencies`, `capabilities`, `apiVersion`) has an exported interface; a package document is data and nothing in it executes.
  - **Isolated example plugin, full cycle per the contract**: the test builds (`contributionIssues` = the build gate for a data package), installs (batch install validates first and writes disabled), enables and disables (republish with `enabled` true/false — the SDK's only switch for data packages), and uninstalls — **without copying any main-app implementation**; `EXAMPLE_PACKAGE` alone carries everything needed.
  - **Compatibility is a rule, not a hope**: older API lines run in `legacy` mode, newer lines are refused before anything is installed, and non-integer versions never pass.
  - **Frontend mounting stays a build-time power**: marketplace packages cannot declare `features`/`frontendModules`/`panels`/`defaultEnabled`; the checklist flags each attempt by name.
  - **Events are namespaced and deduplicated** under the owning package id, so two plugins can never collide on an event name.
